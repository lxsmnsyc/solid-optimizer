# Debate: Choose what to add to or expand in the Solid 1 optimizer (main branch, published 0.4.0) for the 0.5.0 release, ranked by bundle-size gain per unit of work

## Settled structure

- P1: Ship first, as one PR: port the untracked-callback rule so components with statements inline inside <For>/<Show>/<Match> callbacks and the render callback. Sound in Solid 1: mapArray runs each item in createRoot (untracked), Show/Match untrack a callback with a parameter, render uses createRoot. Targets no-host 15 + copy-no-host 9 on solid-ui and 2 on hackernews (Comment recursion stays). (1.5 hours, ~25 solid-ui calls, est. 0.2-0.5 kB min)
- P4: Do not port the Solid 2 <For> unroll, <Dynamic> fold, or JSX-arrow reduction as headline work: the example apps have 0 <Dynamic>, 0 literal <For each={[...]}>, and 1 <For> over a constant list. The Solid 2 demo gain (-28..-32%) came from the whole app turning static so className/classList/effect helpers vanish; solid-ui and hackernews stay dynamic so that does not transfer. Port only the <For> unroll if time is left (about 1 h), because Solid 1 For has the same shape, but expect gains only in static-content apps. (0.5 kB gzip on solid-ui, est. from 1 constant For)
- A1: Cheapest path to the same goal: release 0.5.0 as P1+P2+P3 only (about 3.5 hours, one cheap PR each), put the saved time into build speed and report coverage, and say plainly in the changelog that the example apps move by at most a few hundred bytes. Solid 1 example gains are 0.2-1.3% gzip and the machine builds solid-ui at 3.9-4.6 s; the leverage is build time (3.5x plain) and not bytes. (3.5 hours)
- P8: Revised 0.5.0 structure: ship P1 (untracked callbacks, keep the Show length>0 rule from O8) as a small correctness-tested PR with the honest note that it moves solid-ui by tens of bytes, plus the docs recommendation of single chunking is NOT claimed (O7 rejected). Nothing else is promised in bytes. (1.5 hours)

## Rejected

- P3: Ship with P1 as cheap rider: fold define and import.meta.env in every build (a00bfc8) and replace constant memos (ff1bf8a). Both are small and independent. Measured pattern count in the example apps: import.meta.env 0, createMemo 2 on solid-ui, 0 on hackernews, so gain on these apps is about zero; value is for user apps with env flags and DEV branches.. Why not: O3: examples have 0 import.meta.env and 2 createMemo constants; chunk mode runs after Vite's define replacement. Keep only as a parity rider if the user wants parity (Q1). (by O3, P7)
- P5: Biggest untouched bucket is copy-package 211 (Kobalte, Polymorphic x35) plus imported 468 on solid-ui, but the optimizer removed only 61 of 916 createComponent calls (6.7%) and most remaining calls are in package code the plugin does not see. Expand with the opt-in optimizer.packages copy (roadmap item 9) gated by the size estimate, starting with Kobalte's Polymorphic and ButtonRoot. Largest possible gain, largest work and risk (solid export condition, package public exports, hydration keys); ship as 0.5.0 experimental or defer to 0.6.0.. Why not: O5: 12 h for an unmeasured gain whose main target (Polymorphic) is blocked by call-spread, call-ref and Dynamic; prior art (roadmap item 9) says package copies add little. Becomes a capped spike. T1 (J10) measured 0 B. (by O5, P7)
- P6: Add a Solid 1 only target: member-tag (20 on solid-ui, 3 on hackernews). Context.Provider in the app's own code (FormControlContext.Provider x5, hackernews Context.Provider x3) could go through the existing provider-removal pass once the context binding is recognized; namespace tags such as dialog_exports.Content are Kobalte and stay out. Needs a read of provider.ts to confirm Solid 1 Provider semantics match.. Why not: O4: the unrecognized providers come from packages, and the router's subtrees stay anyway (roadmap step 0). (by O4, P7)
- A2: Different lever: a pure post-bundle size pass is not needed; instead grow the gate. Lower the cost of the 'imported' (468) and 'copy-size' (286) decisions by revisiting default chunking: single chunking gives -1.3% on solid-ui versus -0.3% default, so a docs/default recommendation (CHUNKS=single or vendor split) gets about 1.8 kB more at no code cost.. Why not: The benchmark sums every chunk; single chunking ships the whole app on first load, so its lower sum is not a size gain for users. It is also not compiler work.
- O7: The measured gap between chunkings is larger than any port: solid-ui default -697 B, vendor -421 B, single -2515 B (-1.3%). 'imported' (468 calls) is the biggest bucket and only exists because the chunk step cannot inline across chunks. Cheapest first step for 0.5.0: measure how much of imported overlaps copy-size/copy-package (the same call is counted twice), then check why Icon x48 (call-spread, Icon wraps splitProps+svg) stays on main while the Solid 2 roadmap says 78 of 94 icon spreads inline there. Fixing that call-site spread difference may be worth more than P1+P2+P3 together, for about the same effort.. Why not: Chunking part: same flaw as A2. Icon part: J9 shows the icon wrappers stay by a measured choice, and inlining Icon into 78 wrappers needs a call-site spread copy (roadmap item 2 step 3, not planned: needs mergeProps). The 'imported' bucket overlaps copy-size and copy-package by construction, since the chunk step reports what copying already declined.
- A3: If P9 finds no group of 20 or more, spend the remaining 0.5.0 time on build time instead of bytes: the optimized solid-ui build takes 3.9-4.6 s against 1.05-1.41 s plain, and the chunk renderChunk step is 34-41% of it (1.1-1.3 s). That is a measured, user-visible gain Q1 does not exclude.. Why not: O10: build time is outside the goal and the user's 'measured gains only' answer is about bundle size; the 1 s bound is also not reachable. (by O10)

## Open risks

- P2 (proposal): Ship second: measure copies with the module's top-level constant data (4424b21) and fold constants exported from JSX modules (e59c432). On Solid 2 the measurement alone inlined Table and Card and cut the demo by 762 B gzip. It targets copy-size 286 and copy-shape 63, the largest decided-by-size buckets on solid-ui, though solid-ui has only 7 top-level array constants, so gain there is probably small.. Open because: Both sides estimate under 0.3 kB on solid-ui with no Solid 1 measurement; the Solid 2 762 B came from a static demo. Settled by the port's own benchmark run.
- P9 (proposal): Only new lever worth a time-boxed look: props-use (56 calls on solid-ui). Registry components already follow the splitProps(props, [..]) + spread pattern the optimizer handles (104 splitProps in 22 registry files), so the 56 refusals are a specific unhandled read of the props parameter (inline.ts:687 and :703). Step one is to print those 56 reads from the main worktree and group them; build only if one group covers 20 or more calls, and ship only with a measured byte delta from OPTIMIZE=1 vite build on solid-ui.. Open because: O9 shows 16 of the 56 named calls are package code that T1 already found refused downstream; the other 40 are unclassified. A 20-minute grouping settles it before any build.
